# objc2-overlay

objc2's published crates with the fixes Sidestep needs before upstream
releases them. The fixes live, one commit each, in Sidestep's objc2 fork,
**github.com/bitemyapp/objc2**, on two branches:

- **`sidestep`**, based on objc2's `objc2-0.6.4` tag, the source objc2
  0.6.4 was released from: all nine commits. The patches to objc2 0.6.4
  follow it.
- **`sidestep-main`**, the same fixes on objc2's `main`, which already has
  commit 1 and no longer has what commit 9 fixes: commits 2 to 8, and the
  ones to send upstream (`sidestep`'s don't apply to `main`). The published
  0.3.2 framework crates were generated by a `main`-era generator, which
  the tag's predates, so the rules for commit 3 follow `sidestep-main`'s
  version of it: only that version keeps AppKit's toll-free bridging to
  CoreText Apple-only and maps malloc zones, since the tag's generator
  emits no bridging and doesn't map `Darwin.malloc`. Commit 8 is a config
  line on `sidestep-main`; on `sidestep` it also teaches the tag's
  generator the function `return` override `main` has.

docs/abi.md says what each one fixes. This tool rebuilds the crates they
change from crates.io's, so neither the fork nor Sidestep has to contain
objc2's generated bindings (docs/legal.md, §3.6).

```sh
cargo run --release --manifest-path tools/objc2-overlay/Cargo.toml
```

writes `.objc2-overlay/<crate>-<version>/` in the Sidestep checkout (ignored
by git) and prints the `[patch.crates-io]` table for it, which Sidestep's
Cargo.toml already has. `scripts/linux-env` and CI run it before cargo. An
app building with Sidestep runs it with `--out DIR` in its own workspace and
adds the table it prints. `--check` only reports whether DIR is up to date;
`--quiet` prints nothing but errors and the table.

For each crate it:

1. takes the `.crate` file from `DIR/.crates`, Cargo's download cache or
   `static.crates.io`, in that order, and checks its SHA-256 against the
   checksum pinned in `src/main.rs` (Sidestep's Cargo.lock had them before
   the patch table replaced those entries); it keeps the checked file in
   `DIR/.crates`, so a rebuild after the tool changes works offline;
2. unpacks it with `tar` and applies `patches/<crate>/*.patch` strictly: a
   hunk that doesn't match exactly where it says stops the tool;
3. for the framework crates, applies the rules in `src/generated.rs`,
   `src/returns.rs` and `src/manifest.rs` to `src/generated/**` and
   `Cargo.toml`;
4. writes a stamp (the tool's version and a hash of its sources, the
   crate's patches and its checksum) and moves the result into place,
   under a lock, replacing the old directory whole.

A crate whose stamp matches is left alone, so a second run does nothing.
Work directories an interrupted run leaves behind (`DIR/.work-*`) go on the
next run.

If Cargo says it failed to read `.objc2-overlay/<crate>/Cargo.toml`, the
overlay hasn't been built yet: run the command above.

The patches are the fork's changes rebased onto the published sources
(which differ from the fork's bases in a few hand-written files), without
changelog entries. objc2's follow `sidestep`, whose files the published
0.6.4 equals, and objc2-foundation's do too, with `src/url.rs` adapted to
the published file. objc2-foundation's `src/tests/string.rs` and
objc2-app-kit's `src/text.rs` come from `sidestep-main`, whose files the
published ones equal (their changes are the same on both branches).

## How the rules are checked

The generated files are changed by rule, never by patch: a patch would
carry generated text as context. The rules work from the text's structure,
the `#[cfg(...)]` attribute lines, the crate features they name, item
headers and extents, and `libc` type names, and copy nothing from it.

`src/returns.rs` finds the functions commits 7 and 8 configure by name,
as the configs name them (the free function, and the associated function
the generator makes from it, which carries the name as its `doc(alias)`),
and rewrites only their return: the return type and the lines after the
call, each rewrite expecting exactly what the generator writes for the
published return.

`src/platform.rs` ports header-translator's `PlatformCfg` (with
`sidestep-main`'s addition for toll-free bridging) and takes each library's
platforms from objc2's translation configs at `frameworks-0.3.2`.
For every item in the seven framework crates (about 46,000) and every
dependency table, the tool derives the platform `cfg` twice: from the
configs the crates were published with, which must reproduce the published
`cfg` exactly or the tool stops, since its model of the generator would be
wrong; and from the fork's configs, which is what it writes. `src/main.rs`
also pins how many gates each crate loses, gains and changes (for
objc2-app-kit: 80 removed, 2 added, the 10 bridging impls kept), and how
many returns commits 7 and 8 change (2 in objc2-app-kit, 2 in
objc2-core-graphics), so any drift stops it too.

Its output was compared with the simulations of the regenerated crates
made while the fork was written (`sim.py`, identical for all six crates it
covers) and with the earlier research ones (which differ only where the
fork decided otherwise: the bridging impls, UniformTypeIdentifiers staying
Apple-only, the Darwin-only types, QuartzCore's Metal and CoreVideo items,
the docs.rs targets and QuartzCore's features). The regeneration itself
belongs to objc2's maintainer; nobody runs header-translator against
Apple's SDK for this.

`cargo test --manifest-path tools/objc2-overlay/Cargo.toml` runs the unit
tests: SHA-256 against known answers, the patch applier, header-translator's
own `PlatformCfg` tests, and the rules (the return rules included) on
made-up inputs in the generator's layout.

## Changing it

A new fix goes to the fork first, as a commit that could be sent upstream.
Then:

- hand-written code: make the change in an unpacked copy of the published
  crate and write the patch with
  `diff -u --label a/<path> --label b/<path> old new`, paths relative to the
  crate. The tool refuses patches that touch `src/generated/`.
- generated code or `Cargo.toml`: add a rule, keyed on structure, check it
  against the published configs where it can be, and update the pinned
  counts.
- a newer published version: update the pin (name, version, checksum from
  the crates.io index) and rebase the patches onto it.

The stamps change by themselves with the sources, so everyone's overlay is
rebuilt on the next run, from the `.crate` files kept in `DIR/.crates`.

## Licence and lifetime

The patches carry objc2's hand-written code (as context and as the fork's
changes), and `src/platform.rs` is a port of header-translator's
`cfgs.rs` with its tests. Both are objc2's code under objc2's licences:
MIT for objc2 and objc2-foundation, and Zlib OR Apache-2.0 OR MIT for
header-translator and objc2-app-kit, -core-foundation, -core-graphics,
-quartz-core, -core-text and -image-io, used here under MIT.
[LICENSE-objc2](LICENSE-objc2) is the notice that goes with them. The
crates the tool writes are objc2's under the same licences. The rest of
the tool is Sidestep's (MIT OR Apache-2.0).

It goes away as upstream releases the fixes: drop each patch and rule once
a release has it, and the tool, the `[patch.crates-io]` table and the steps
that run it once nothing is left (docs/abi.md).

Building a crate path-patched this way shows its warnings, which Cargo
hides for crates.io dependencies; commit 9 is there so that objc2 0.6.4
has none (it declared negative impls behind a disabled feature, which
newer compilers warn about).
